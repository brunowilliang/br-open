## Visão geral

Auth é Better Auth (`better-auth@1.6.24` + `@better-auth/expo@1.6.24`) sobre Convex via kitcn: servidor em `convex/functions/auth.ts` (`defineAuth`), client `authClient` em `src/lib/convex/auth-client.ts`. Este doc cobre o domínio **Conta do usuário** — login, senha, e-mail e contas vinculadas. Ator ativo, playerProfile, organizations e triggers de auth ficam em [organization.md](organization.md).

Toda a área de Login e segurança (página `/settings/security`) usa API **nativa** do `authClient` — zero procedure CRPC própria, zero tabela/migration nova.

### Username (identificador único — plugin `username` do better-auth)
- **Status:** implementado (backend + UI — 22-08-2026, IBX-0010 slice 1; pré-requisito do convite de dupla em torneios; campo do perfil obrigatório desde 21-09-2026, IBX-0079)
- **Data:** 22-08-2026
- **Referências:** `convex/functions/auth.ts` (`username()` no array de plugins), `src/lib/convex/auth-client.ts` (`usernameClient()`), `convex/domains/auth/tables.ts` (`user.username` `.unique()` + `user.displayUsername`), índice `user.user_username_unique` (criado no deploy de 22-08 em dev e prod); UI: `src/app/(private)/settings/player/profile.tsx` (campo no bloco Detalhes, seed de `session.user.username`, `updateUser` no submit), `src/components/pages/player/profile-details-section.tsx` (Controller username), `src/lib/account/username-rules.ts` (regras puras + testes), `src/lib/account/use-username-availability.ts` (debounce + query), `src/lib/account/security-errors.ts` (mapa dos 4 erros)
- **Decisões:**
  - Defaults do plugin (verificados no source 1.6.24): 3–30 chars, validador `/^[a-zA-Z0-9_.]+$/`, normalização **lowercase** (o valor canônico é sempre minúsculo), unicidade garantida por índice unique do Convex + checagem do plugin (`USERNAME_IS_ALREADY_TAKEN`).
  - A opção `displayUsername: false` do design NÃO existe nesta versão (1.6.24) — o plugin não tem essa option nem no server nem no client (`usernameClient()` é zero-args). O intent é atendido por **não expor** displayUsername na UI; a coluna `user.displayUsername` é técnica (exigida pelo schema do plugin) e fica **sempre null neste app**: o auto-fill do databaseHook só roda no create com username no corpo (sign-up), e o sign-up do app não envia username.
  - **Login continua por e-mail** (campo existe, mas o sign-in por username do plugin não é usado — fora de escopo v1, ver tournaments.md).
  - Sem procedure CRPC nova e sem migration: `updateUser({username})` e `isUsernameAvailable({username})` são endpoints nativos do authClient; campos opcionais novos em tabela existente são backward-compatible (regra do guia).
  - Erros nativos (i18n pt-BR confirmado em produção): `USERNAME_TOO_SHORT`/`USERNAME_TOO_LONG`/`INVALID_USERNAME`/`USERNAME_IS_ALREADY_TAKEN`.
  - **A obrigatoriedade é do CAMPO do perfil, não do schema** (21-09-2026, IBX-0079): `user.username` continua **nullable** (`convex/domains/auth/tables.ts`) e o sign-up não envia username; o `player.profile.upsert` não recebe nem valida username (o builder do form faz `.pipe(upsertPlayerProfileSchema)`, que descarta o campo, então username nunca entra no payload do perfil). O único caminho que grava o valor é o `updateUser({username})` do form, que a partir daqui não aceita mais vazio. Exigir username como invariante de domínio (gate no servidor, "todo jogador tem username") é mudança de backend e não está implementado.
- **Como funciona (UI):** campo "Username" no bloco Detalhes do perfil (aberto direto na tela, IBX-0063) (`variant="secondary"`, `autoCapitalize="none"`), **obrigatório** (IBX-0079): vazio (ou só espaços) barra o submit com "Informe um username." (`USERNAME_REQUIRED_MESSAGE`, via `validateUsernameField` no refine do schema do form). Validação client espelha os defaults do servidor (`validateUsernameFormat`: 3–30, `[a-zA-Z0-9_.]`, dica enxuta "3 a 30 caracteres, apenas letras, números, ponto e underline."); disponibilidade ao vivo via `useUsernameAvailability` (debounce 500ms → `authClient.isUsernameAvailable`, React Query com key `["auth","username-available",<username>]`; só consulta com formato válido e valor ≠ username atual; estados idle/checking/available/taken — taken vira FieldError, available vira Description verde `@username está disponível.`). Submit: campo obrigatório — o ramo antigo do username que "não pode ser removido" (`resolveUsernameSubmitIssue`) foi removido junto, porque o vazio já é erro do schema; se mudou, `authClient.updateUser({username})` roda ANTES do upload do avatar e do `player.profile.upsert` (falha aborta o save com toast `getSecurityErrorMessage` + FieldError; sucesso sincroniza o form). O `session.refetch()` roda no FIM do submit (após o `upsert`), nunca no meio — refetch intermediário dispararia o efeito de hidratação com `playerProfile.data` stale e reverteria no form edições não salvas se uma etapa posterior falhasse. O servidor valida tamanho/charset, normaliza para lowercase, checa unicidade e grava `username`. O endpoint público `POST /api/auth/is-username-available` responde `{available}` (verificado vivo em dev `kindred-yak-142` e prod `amiable-albatross-845` em 22-08).

### Redefinição de senha por OTP (logado, sem sair da sessão)
- **Status:** implementado (contrato backend 100% nativo + dialog UX `src/components/pages/player/forgot-password-dialog.tsx` — IBX-0007 QA round 4)
- **Data:** 16-08-2026 (IBX-0007 QA round 4)
- **Como funciona** — o item "Esqueci minha senha" da seção Segurança abre um dialog (mesmo padrão do dialog de troca de e-mail) que NÃO desloga. Sequência nativa (zero procedure/tabela/migration):
  1. **OTP para o e-mail ATUAL**: `authClient.emailOtp.requestPasswordReset({email})` (`/email-otp/request-password-reset`, público) — código tipo `forget-password`, assunto "Código BR Open para redefinir sua senha". Anti-enumeração nativa: e-mail inexistente responde `{success: true}` sem enviar.
  2. **(gate de UX, opcional)** `authClient.emailOtp.checkVerificationOtp({email, otp, type: "forget-password"})` — verifica SEM consumir o código no sucesso; tentativa errada soma attempt. Mesmo gate do fluxo público (`forgot-password.tsx`).
  3. **Nova senha**: `authClient.emailOtp.resetPassword({email, otp, password})` — consome o OTP, valida 8–128 chars (default do better-auth), atualiza o hash da credential e NÃO mexe em sessões (a config global `revokeSessionsOnPasswordReset` NÃO é ligada — ela revogaria TODAS, incluindo a atual). Side effects: cria a conta credential se não existir (conta só-social ganha senha por aqui) e marca `emailVerified: true` se ainda não era.
  4. **Revogar outras sessões**: `authClient.revokeOtherSessions()` (`/revoke-other-sessions`) — revoga todas exceto a atual, espelhando o `revokeOtherSessions: true` do changePassword. Chamar SEMPRE depois do passo 3; se falhar aqui, a senha já foi trocada e NÃO há rollback.
- **Semântica de sessão** (default do card, confirmada no source): sessão atual mantida (nenhum passo invalida o token atual), outras sessões revogadas no passo 4. Divergências vs changePassword, deliberadas: (a) o passo 4 usa `sensitiveSessionMiddleware` — sessão com ≥24h → `SESSION_NOT_FRESH` (senha já trocada, outras sessões não revogadas; tratar com o padrão do unlink: toast + sign-out guiado); (b) o token da sessão atual NÃO é rotacionado (no changePassword um token novo volta na resposta).
- **Erros:** `OTP_EXPIRED` / `INVALID_OTP` / `TOO_MANY_ATTEMPTS` (código descartado após 3 erros) / `PASSWORD_TOO_SHORT`·`PASSWORD_TOO_LONG` (default 8–128) / `USER_NOT_FOUND` (check com e-mail inexistente). Rate limit reusado do emailOTP: bucket próprio 3 req/60s por endpoint.
- **UX (dialog):** 2 steps no padrão do `change-email-dialog.tsx` — código (`InputOTP` slots `variant="secondary"`, reenvio com `useOtpCooldown` key `otp-forgot-password-timestamp` 60s, gate `checkVerificationOtp` que NÃO consome o código) e nova senha (`PasswordInput variant="secondary"`, zod 8–128 + confirmação). Sucesso: `resetPassword` → `revokeOtherSessions` (outcome `revoked` fecha o dialog + toast de sucesso; `warned` fecha com aviso de que outros dispositivos não caíram; `SESSION_NOT_FRESH` fecha com toast + sign-out guiado, padrão do unlink — a senha já foi trocada, sem rollback). O usuário CONTINUA LOGADO em todos os caminhos exceto o sign-out guiado; a linha "Esqueci minha senha" não tem mais gate de `signOut.isPending` (o sign-out preventivo foi removido junto com o `handleForgotPasswordPress`). Erros do mapa `security-errors.ts`: `PASSWORD_TOO_SHORT`, `PASSWORD_TOO_LONG`, `USER_NOT_FOUND` adicionados em 16-08 com testes co-located.
- **Layout dos steps com OTP (QA round 5, vale para os 2 dialogs):** ordem título → descrição → OTP → bloco de reenvio → botão; `InputOTP` centrado no card via `className="self-center"` no root (o root aceita `className` — source input-otp.tsx:54; equivalente ao `items-center` do container público `forgot-password.tsx:218`, sem margem fixa); a linha de reenvio `View` `flex-row flex-wrap items-center gap-1 self-center` com o timer MMSS dentro do fluxo (sem `ml-2` avulso). A ordem vale para TODOS os steps com OTP, incluindo o passo 2 do change-email (código do e-mail novo, QA round 8), que tem o mesmo bloco de reenvio centralizado entre o OTP e o botão (ver seção "Troca de e-mail").
- **Balde único abertura+reenvio (QA round 6; envio-na-abertura só no forgot-password desde o QA round 8):** a abertura do forgot consulta o cooldown PERSISTIDO da mesma key do `useOtpCooldown` (`shouldSendOtpOnOpen` em `src/lib/account/otp-open-send.ts`, teste co-located — `null`/inválido envia, cooldown ativo NÃO envia (o código anterior ainda é válido, o timer já roda no bloco de reenvio), fronteira/expirado envia, clock-skew futuro conta como ativo); reabrir dentro dos 60s não empilha códigos no inbox. No change-email (2 passos, QA round 8) NÃO há envio na abertura — o balde vale só para o submit do passo 1 e o reenvio do passo 2 (mesma key `otp-change-email-new-timestamp`). Auto-validação: TODOS os steps com OTP têm `onComplete` (6 dígitos disparam a ação sozinhos, respeitando `isPending`; no forgot valida o código, no change-email submete o `changeEmail`) — o botão segue como fallback de acessibilidade. ### Troca de e-mail com OTP (código único, só no e-mail NOVO)
- **Status:** implementado (backend + dialog UX em 2 passos `src/components/pages/player/change-email-dialog.tsx` — IBX-0007 QA round 8)
- **Data:** 16-08-2026 (QA round 8; substitui o fluxo duplo de 14-08)
- **Config:** `changeEmail: {enabled: true, verifyCurrentEmail: false}` nas options do plugin `emailOTP` (`convex/functions/auth.ts`). `enabled: true` liga os endpoints (sem ele: 400 "Change email with OTP is disabled"). `verifyCurrentEmail: false` — decisão de produto do QA round 8: o step do código do e-mail atual foi reprovado (o client nunca o validava de verdade — bug confirmado, qualquer código avançava; a verificação real só acontecia no submit final) e o fluxo duplo foi considerado errado. A prova de posse é só o e-mail NOVO.
- **Contrato client (exato):**
  1. `authClient.emailOtp.requestEmailChange({newEmail})` — POST `/email-otp/request-email-change` (sessão obrigatória + fresca <24h). Com `verifyCurrentEmail: false` o campo `otp` NÃO é enviado (passá-lo só gera warning no log do servidor). Valida formato (`INVALID_EMAIL`) e `newEmail !== email atual` ("Email is the same"); gera OTP tipo `change-email` (identifier `"change-email:<atual>-<novo>"`, 6 dígitos, 300s, 3 tentativas) e envia ao e-mail NOVO (assunto "Código BR Open para trocar seu e-mail", copy de `buildOtpEmail`). **Anti-enumeração**: `newEmail` já existente → `{success: true}` SEM envio (código descartado) — copy neutra; o conflito só aparece no passo 2.
  2. `authClient.emailOtp.changeEmail({newEmail, otp})` — POST `/email-otp/change-email` (sessão obrigatória + fresca). Verificação ATÔMICA de consumo único (`atomicVerifyOTP`): erra → código NÃO é consumido (attempt +1; 3 erros = `TOO_MANY_ATTEMPTS` FORBIDDEN e identifier travado); acerta → consome. Depois do OTP válido: `USER_NOT_FOUND` (não deve ocorrer) e "Email already in use" — única revelação do conflito, segura porque o usuário provou posse do novo e-mail. Sucesso: `user.email = newEmail`, `emailVerified: true`, cookie da sessão re-setado com o e-mail novo — sessão atual mantida, outras sessões NÃO revogadas.
  - **Não existe pré-check não-consumível para este OTP**: `checkVerificationOtp` faz `findUserByEmail(email)` antes de verificar, e o identifier é composto (`<atual>-<novo>`) → `USER_NOT_FOUND`; não há endpoint `verifyChangeEmailOTP` no plugin (exports: send/verify-email/check/request-password-reset/reset-password/forget-password/sign-in/request-email-change/change-email). A UI submete direto ao `changeEmail`.
- **Erros UI:** `SESSION_NOT_FRESH` (ambos os endpoints — sessão ≥24h; padrão do unlink: fecha dialog + toast + sign-out guiado), `UNAUTHORIZED`, `INVALID_EMAIL`, "Email is the same", `OTP_EXPIRED`, `INVALID_OTP`, `TOO_MANY_ATTEMPTS`, "Email already in use", 400 "Change email with OTP is disabled" (flag off — não é o caso). Mapa em `src/lib/account/security-errors.ts`.
- **Referências (UI):** `src/components/pages/player/change-email-dialog.tsx` (dialog em 2 passos: novo e-mail → código único no novo e-mail, com "Reenviar código"), `profile-security-section.tsx` (item "Alterar e-mail")
- **UX (dialog 2 passos, QA round 8):** passo 1 = input novo e-mail (zod email, `variant="secondary"`, done) → `requestEmailChange`; passo 2 = `InputOTP` 6 slots `secondary` `self-center` com `onComplete` = SUBMIT DIRETO do `changeEmail` (não existe pre-check — o submit é a validação; botão "Confirmar troca" mantém a mesma ação) + bloco de reenvio centralizado entre OTP e botão (padrão QA R5) chamando `requestEmailChange` de novo (mesma key de cooldown `otp-change-email-new-timestamp`, 60s, iniciado em qualquer tentativa). `SESSION_NOT_FRESH` em qualquer passo → fecha dialog + toast + sign-out guiado (padrão do unlink). Sucesso → `refetchSession` + toast + fecha (sessão mantida, outras não revogadas). Layouts QA R5–R7 preservados (Close fora do Pressable, dismiss por toque). Sem envio na abertura — o gate `shouldSendOtpOnOpen` permanece só no forgot-password.
- **Cooldown/reenvio:** reenvio = chamar `requestEmailChange` de novo (gera código NOVO no identifier `<atual>-<novo>`); bucket 3 req/60s do endpoint + cooldown UI 60s (`useOtpCooldown`, padrão do balde único da QA round 6).

### Contas vinculadas (listar / conectar / desconectar)
- **Status:** implementado
- **Data:** 14-08-2026 (IBX-0007)
- **Referências (UI):** `src/components/pages/player/linked-accounts-section.tsx`; a query de contas vive na tela (`src/app/(private)/settings/security.tsx`) com chave `authAccountsQueryKey` (`["auth","list-accounts"]`) e as linhas são derivadas de `buildLinkedAccountRows` (`src/lib/account/linked-accounts.ts`, ordem fixa credential/apple/google)
- **Como funciona:**
  - Listar: `authClient.listAccounts()` → `{providerId, accountId, ...}` sem segredos. E-mail+senha aparece como `providerId === "credential"` — linha INFORMATIVA no padrão das outras de status (QA round 8: "Conectado./Não conectado." no `ItemDescription`, SEM clique e SEM botão — "Alterar senha" já vive na Segurança; desvinculada mantém `opacity-50` + "Não conectado.").
  - Conectar Apple: no iOS, fluxo nativo (`expo-apple-authentication` — guard `isAvailableAsync`, `signInAsync` + `linkSocial({provider: "apple", idToken})` com o identityToken); fora do iOS cai no OAuth web (`linkSocial({provider: "apple", callbackURL})`), mesmo caminho do Google.
  - Conectar Google: `authClient.linkSocial({provider: "google", callbackURL})` — OAuth web via proxy do `expoClient` (`Browser.openAuthSessionAsync`).
  - Desconectar: `authClient.unlinkAccount({accountId: <id LOCAL da row>})` (Better Auth 1.7: o seletor é o id da row em `account` devolvido por `listAccounts` — o seletor antigo `{providerId}` da 1.6 não existe mais) → invalidate da query de contas + toast.
- **Proteções nativas (mantidas por decisão de segurança), mapeadas em `security-errors.ts`:**
  - `FAILED_TO_UNLINK_LAST_ACCOUNT` — nunca desconecta a última forma de login → "essa é sua última forma de login — conecte outra antes de remover".

## Decisões tomadas

- Segurança de conta 100% via API nativa do better-auth (`authClient.*`): nenhuma procedure/tabela/migration própria para troca de senha/e-mail ou contas vinculadas.
- Troca de e-mail usa código ÚNICO no e-mail novo (`verifyCurrentEmail: false`, decisão de produto do QA round 8) — o fluxo duplo foi reprovado: o step do código do e-mail atual nunca validava no client e só adicionava fricção; a prova de posse do novo e-mail é o gate de segurança.
- Anti-enumeração preservada e copy neutra no pedido; conflito de e-mail só revelado na confirmação.
- Bloqueio padrão de Apple Hide My Email mantido (não vinculamos Apple ID de e-mail diferente do e-mail da conta).
- `freshAge` global (24h default) intocado: sessões velhas reautenticam pontualmente nos endpoints sensíveis (unlink, troca de e-mail) em vez de encurtar a vida de todas as sessões.
- E-mails transacionais em pt-BR, um único template `<p>` com o código em `<strong>`; o tipo `change-email` só muda assunto/corpo, não o layout.
- Redefinição de senha logada 100% nativa (`requestPasswordReset` → `resetPassword` → `revokeOtherSessions`): nenhuma action custom — reimplementaria o verifyOTP interno do plugin; a revogação das outras sessões roda DEPOIS do reset e exige sessão fresca (mesmo middleware do changePassword).
