Os componentes de KPI/gráfico para estes dados serão DEFINIDOS E APROVADOS item a item antes de voltar
- **Data:** 19-09-2026 (em andamento, sem commit)
- **Referências:** convex/functions/player/dashboard.ts (`getOverview` authQuery, input `{ months?: 1..24 }`, default 6); convex/domains/player/contract.ts (`playerDashboardOverviewSchema` + `playerDashboardPlayerCardSchema`, `playerDashboardUpcomingMatchSchema`, `playerDashboardResultMonthSchema`, `playerDashboardPositionPointSchema`, `playerDashboardLeaguePositionSchema`, `playerDashboardEntryCategorySchema`, `playerDashboardPartnerSchema`); convex/domains/player/dashboard-rules.ts (`brazilDayKey`, `classifyResultOutcome`, `bucketResultsByMonth`, `buildPositionSeries`, `findMostFrequentPartner`, `countActiveEntriesByCategory`); convex/domains/payment/rules.ts (`buildBrazilMonthKey`, `buildRecentMonthKeys`, `monthKeyWindowStartMs`); convex/domains/player/tests/dashboard-rules.test.ts.
- **Shape:** `{ upcomingMatches[], performance { wins, losses, winRate 0..1, byMonth[{month,wins,losses}] }, leagues[{leagueId, leagueName, membershipId, position, rankingSize, series[{at,position}]}], entryCategories[{categoryId, displayName, entryCount}], frequentPartner {count, player{playerProfileId, fullName, avatarUrl}} | null }`. `upcomingMatches[]` = `{ id, kind: "league_challenge"|"tournament_match", competitionId, competitionName, categoryId, categoryDisplayName, matchDate "YYYY-MM-DD", startMinute, endMinute, courtName, partner|null, opponents[] }`, ordenado por (matchDate, startMinute), limite 20.
- **Como funciona:** exige ator player (`requireActivePlayerProfile`, FORBIDDEN caso contrário). Ligas = memberships `active` (índice `playerProfileId_status`; mesmo conjunto do `league.discovery.listParticipating`). Próximos jogos de liga = desafios `confirmed` com proposta atual a partir de hoje (mesma semântica do `league.challenges.listScheduled`); `matchDate` comparado por chave de dia do BRASIL (`brazilDayKey`), divergindo da agenda da liga (que usa UTC) só na janela 21:00–23:59 BRT — escolha documentada: o produto segue o calendário do Brasil. V/D de liga = desafios `finished` dentro da janela; vencedor vem do `latestResultSubmission.winnerMembershipId` (o desafio não guarda vencedor). V/D de torneio = matches `finished` com `winnerEntryId` em entradas minhas (não canceladas) dentro da janela; W.O. de SORTEIO (bye: `walkover` sem `publishedAt`) NÃO conta como resultado. Série de posição por liga = `rankingSnapshotAfterResult` dos desafios `finished` com participação do viewer (posição = índice do membershipId no snapshot, 1-based; timestamp = `rankingAppliedAt` com fallback `finishedAt`; mesmo instante mantém o snapshot mais novo; últimos 24 pontos; `rankingSize` = tamanho do último snapshot, escala do eixo Y). Inscrições por categoria = entries `active` agrupadas por categoria (decisão do doc: distribuição só de confirmadas). Parceiro frequente = duplas não canceladas dos dois lados (playerA ou playerB), desempate count → entrada mais recente → id. Wins/losses/winRate = totais da janela (consistente com `byMonth`).
- **Decisões:** leituras limitadas; indexadas onde o índice existe (20 ligas via `playerProfileId_status`, 200 desafios por lado/liga via `challenger|challengedMembershipId_status`, 50 matches por query via `entryAId`/`entryBId`, 20 upcoming; proposals e submissions por `challengeId*`). EXCEÇÃO assumida: as buscas de entries por `playerAId`/`playerBId` isolados NÃO têm índice próprio (só os compostos `categoryId_playerXId`, `domains/tournament/tables.ts`) e rodam como scans limitados (100 por lado) — o MESMO padrão pré-existente do `tournament.discovery.listParticipating`, sem regressão; índice próprio é trabalho futuro (migration, fora do corte read-only). Profile lookup com cache por playerProfileId e degradação para placeholder quando um perfil sumiu (o dash não pode 500 por causa de uma linha órfã); positions series NÃO é recortada pela janela de meses (é histórico por resultado, cap 24). O agregado é composto dos buckets existentes — sem tabela nova; se V/D global precisar escalar além dos limites atuais, a decisão de índice/view materializada fica registrada como trabalho futuro (não inventado agora).
